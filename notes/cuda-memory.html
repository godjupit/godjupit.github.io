线程组织与内存访问

理解 CUDA 程序如何组织线程、隐藏访存延迟、使用全局与共享内存，以及推理侧 KV Cache 如何按前缀复用。

线程层次：Thread、Block 与 Grid

CUDA 程序以线程为基本执行单元。线程组成线程块（thread block），线程块再组成网格（grid）；一次 kernel 启动对应一个 grid。硬件以线程束（warp）为单位调度执行，常见 NVIDIA GPU 的 warp 包含 32 个线程。

线程块会被分配到某个流式多处理器（SM）上执行。一个 SM 能同时驻留多少线程块，取决于线程数、寄存器和共享内存等资源。线程块一旦开始执行，就由该 SM 完成；不同线程块的执行先后顺序不应由程序假定。

在支持双发射的架构上，一个 warp 调度器每个时钟周期可以从同一指令流中发出两条相邻指令。典型 GPU 的一个 SM 最多驻留 64 个 warp（约 2048 个线程），因此线程块大小通常取 32 的整数倍。

用并发隐藏访存延迟

访问显存的延迟通常远高于简单算术运算：读取全局内存往往需要一百个时钟周期以上，而多数计算指令只需几个到几十个周期。某个 warp 因数据尚未就绪而停顿时，调度器可以切换到其他就绪的 warp 执行，让计算与等待交叠。这称为延迟隐藏（latency hiding）。

kernel 需要足够的并行工作供硬件调度，教学材料中常提到每个 SM 512–2048 线程这一经验区间；但线程数并非越多越好：寄存器、共享内存等资源会限制驻留数量，最终应结合目标 GPU 和实际测量调整。

全局内存与合并访问

全局内存访问通常以硬件事务或内存段为单位完成，而不是为每个字节单独发起传输。同一个 warp 中的线程若访问相邻、对齐的数据，硬件往往能用较少的事务满足请求；地址分散时，可能需要更多事务，降低有效带宽。

具体事务大小和行为取决于 GPU 架构、数据类型与访问模式。分析时应关注线程地址如何分布，并用性能分析工具验证，而不要把某个固定字节数当成所有设备都适用的规则。

共享内存与 Bank Conflict

用 __shared__ 声明的数组位于共享内存中，由同一线程块里的线程共同使用；不同线程块拥有彼此隔离的共享内存区域。共享内存按 bank 组织，不要求访问地址连续；与全局内存的合并访问不同，这里关键是同一 warp 的访问是否分散到不同 bank。

常见硬件将共享内存划分为多个 bank；在典型的 32-bank、32 位访问场景中，连续线程访问连续 word 通常可以并行完成。

若 warp 中线程 t 访问 sdata[t]，访问通常分散到不同 bank。若访问 sdata[t * 32]，这些地址在该模型下落入同一 bank，形成 bank conflict，访问会被拆成多次处理。实际行为仍需结合设备架构、访问宽度和广播规则判断。

// 连续访问：通常可分散到不同 bank
value = sdata[threadIdx.x];

// 在典型 32-bank 模型下可能产生 bank conflict
value = sdata[threadIdx.x * 32];

线程块内同步

__syncthreads() 是线程块级屏障：同一线程块中参与该屏障的线程都到达后，才能继续执行后续代码。常见用法是让线程协作加载共享内存数据，再同步一次，确保数据准备好后才开始计算。

屏障不能只被线程块中的部分线程执行。若把它放进条件分支，必须保证同一线程块中所有相关线程以一致方式到达屏障，否则程序行为不正确。

并行规约与原子操作

规约（reduction）把大量数据合并成少量结果。经典做法是让线程两两配对、逐步对折合并，最终每个线程块得到一个部分和。

把各块的部分和汇总到同一个地址时，常用 atomicAdd：硬件把读取、修改、写回作为一个不可分割的整体完成，避免并发的读改写互相覆盖。

网格 stride 与矩阵写法

处理矩阵这类连续数据时，可以把全局下标当作由线程共同覆盖的一个循环：每个线程先取一个下标，之后每次前进一个“网格总步长”，按 stride 把数据走完。

size_t idx = threadIdx.x + blockDim.x * blockIdx.x;
const size_t stride = blockDim.x * gridDim.x;  // 整个网格一次能覆盖的元素数

共享内存是每个线程块一份，总量由硬件决定；怎么切给每个块由 kernel 的写法决定，最终能同时驻留多少块由 GPU 调度。按块划分共享内存、再按 stride 覆盖数据，是矩阵类 kernel 的常见组织方式。

延伸：KV Cache 与前缀缓存

在推理中，prefill 阶段会把整段 prompt 一次性喂给模型，计算并保存对应的 KV Cache，供后续逐 token 的解码复用。

前缀缓存（prefix cache）按块复用这些结果：每个块都会根据内容计算一个哈希，并叠加所在前缀的哈希，因此块的身份是上下文相关的：同一段内容只有跟在相同前缀后面时，哈希才一致、才能复用。例如块 A={1,2,3,4} 的哈希记为 H1，其后的块 B 的哈希则由 H1 与 B 的内容共同决定。
